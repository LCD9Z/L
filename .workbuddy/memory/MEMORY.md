### 其他已踩过的接口/格式坑

| 项 | 坑 | 正确做法 |
|---|---|---|
| 通达信 `.day` | 32 字节/条，`<IIIIIfII`，价格 ÷100 | **首条=最早**，末条=最新（可直接 seek 读） |
| `.day` 首条日期 | 无「读首根」API，`read_day_tail` 读的是**尾部** | 直接二进制读前 32 字节 |
| 腾讯 secid | 东财是 `1.600000`；**baostock 是 `sh.600000`** | 两库格式不同，勿互抄 |
| 腾讯 volume | **分板块**：`sh688`=股，其余=手（须 ×100） | 见 `AGENTS.md` |
| baostock volume | 与通达信**逐位相同**（都是股） | 不需换算 |
| JSON 落盘 | `open(p,'w')` 在 Windows 会转 **CRLF** → `test_line_endings_are_lf` 失败 | 必须 `newline='\n'` |
| baostock 2000 | 是「**一页**」不是上限；`next()` 失败会**静默返回 False** | 判据 `n % 2000 == 0` ⇒ 须复核 |

## 本项目的「静默失效」坑

### `reports/` 是**白名单制**：新建子目录不补白名单 → 文件**永远不入库**

`.gitignore` 结构是 `reports/*` + 逐条 `!reports/<子目录>/` 白名单。
**新建 `reports/<新子目录>/` 时，若不补
`!reports/<新子目录>/` 与 `!reports/<新子目录>/*`，
该目录下所有 JSON/MD 会被静默忽略 —— 从未 `git add`、也不在 `EVIDENCE_INDEX.md`。**

**⚠️ 2026-10-13 踩到**：`reports/xsource/XSRC.json`（**P0-1 正式结论**）
因此**从未入库**；而 `tests/test_data_asset_registry.py` 只从**磁盘**读该文件
→ **测试全部通过**，完全发现不了「文件根本没进版本库」。
`EVIDENCE_INDEX.md` 由 `git ls-files` 生成，校验用例又比对「索引 vs git」——
两者**一致地缺失**，反而无告警。**这就是静默失效的典型形态。**

**教训**：
- 新建 `reports/` 子目录后，**必须**补两条白名单，
  并跑 `gen_evidence_index.py` 确认**证据份数增加**
- **「读磁盘能通过」≠「文件入库」**：判定类产物的守卫必须查 `git ls-files`
  （已加 `test_official_verdict_artifacts_are_git_tracked`）

## 「跨侧断言须在对象所在侧执行」——**对预注册同样适用**（2026-10-14）

**教训**：一份写得再细的预注册，只要**事实基取自「非执行侧」**，
就会在治疗执行的那一刻**全部失效**（行号、参数、引证文件都对不上）。

实例（P011 / P005 §3.3 预注册）：
| 事实基 | 副本（撰写侧） | **主干（治疗执行侧）** |
|---|---|---|
| 根因行号 | `run_five_factor_ab.py:252` | **`:310`** |
| `run_tdx_rolling_eval.py` | 有 `--ew-benchmark`（现算机制） | **无此参数**（同形隐式兜底） |
| 引证 JSON | `five_factor_ab_v2.json` 存在 | **不存在** |
| `git ls-files reports/*.json` | 58 | **82** |
| `.gitignore` 白名单 | `28-30` | **`34-52`**（逐子目录） |

→ **后果**：预注册判「治疗范围 = 1 个脚本」，**实为 2 个**
（主干 `run_tdx_rolling_eval.py:128` 与 five_ab 同形根因）。

**做法**：
- 预注册里凡引用**代码行号 / 参数名 / 产物文件 / 计数**，
  必须标**侧别**（〔主干〕/〔副本〕/〔两侧同〕）并附**该侧**命令+输出+HEAD
- 治疗执行方 ≠ 事实采集方时，**执行方必须自行复测并回执差异**，
  不得默认「来件数字可直接用于本侧」
- 两份同名脚本**内容可能不同**（冲突文件）→ 用 `git hash-object` 比对，别按名字假设一致

## 两库合并（P006 A2）：**执行侧决定 `ours`/`theirs` 指向**（2026-10-14）

**陷阱**：`git merge X` 时 **`--ours` = 你**当前所在分支**、`--theirs` = 被合并进来的 X**。
与「谁的改动更新 / 谁是新来的」**无关**。

**本项目实例**：A2 **执行侧＝副本**（用户 10-14 定），主干是被合并方 ⇒
**副本执行时：`--ours` = 副本、`--theirs` = 主干**。
所有「取主干版」必须写 **`--theirs`**，并在执行前**自证侧别**
（如 `git show ":3:run_daily.bat" | head -3` 应是主干版特征）。

→ **教训**：合并脚本/清单**必须标注执行侧**；「取我方版/取对方版」这种措辞
在换执行侧后会**整体反转**，是典型「跨侧断言未标侧别」的翻版。

### 冲突类型决定 union 写法
`git merge-tree` 的 AA（仅 stage 2/3）＝ **merge-base 无该文件** ⇒
用 `git merge-file --union` 时 **base 须用空文件**；UU（有 stage 1）才用 `:1:<path>`。

## 「改动守卫自身」必须附**反向验证**（2026-10-15，A2 实例）

**教训**：**测试全绿 ≠ 纪律成立**。改守卫自身（正则/判据/跳过条件）的提交，
若只验证「测试仍通过」，会把**守卫失效**掩盖成**全绿**。

实例：A2(`86956c8`) 为兼容 `**状态**：**值**`，把 `_status` 正则改成
`\**([^\n|*]+?)\**` —— **非贪婪 `+?` + 尾部 `\**` 可匹配 0 个星号**
→ 捕获组只吃 1 字符（`已完成（…）`→`已`）。判定是 `k in st`（子串包含），
`"已执行" in "已"` = False → **核心守卫整片失效**（需产物 **0 份** vs 修复后 **9 份**）。
副本「CI 6/6、pytest 1,263 项全绿」正是在此状态下取得。

**做法**：
- 改守卫代码时，**必须**另加一条反向验证：
  「改动后该守卫**仍能抓到**已知问题」（如钉死 4 种写法的解析结果 +
  断言解析长度 ≥3 且命中判据）
- **非贪婪 + 可选量词**是高危组合：捕获组会被压到最短，
  而 `子串 in 短串` 恒 False → 静默失效。宁可先剥包裹再贪婪捕获。
- 引用他人「CI 全绿」结论时，注明**是否覆盖该纪律的守卫当时有效**

## 复核合并结果：**看提交，不看暂存区**（2026-10-15）

**教训**：`git status` / 暂存区显示「取某侧版」**可能只是中间态**，
执行方在提交前还会人工合并。复核必须查最终对象：
`git show <commit>:<path>`（而非 `git show :2/:3:<path>` 或 status 分类）。

实例：主干据暂存区判 `portfolio_backtest.py`「取副本版 → 丢参数」并告警；
实际提交 `86956c8` 是**人工合并**（189 行，主干 6 钩子 + 副本 `stop_atr_k`/`weight_func`），
**告警是误报**。→ 判断前先确认看的是哪一层。

## 判据有适用边界：「数字链自洽」只判**同型**产物（2026-10-15）

副本判据「产物数字与其**生成侧**预注册记录一致者权威」——合理，
但**只适用于两侧是同一实验**。若**同名不同实验**（数据源/股票数/键都不同），
「谁预注册记了数字」只反映**文档完备度**，不反映**正确性** → 会静默删掉另一份证据。

判据前置步骤：**先比键结构与数据源**确认同型，再谈权威。
实例：`decay_h5/h10/h20` 主干 1500 股/10 键（含 `composite_ic`）vs
副本 400 股/4 键 —— 不同实验，应**改名保留两份**。
铁证形态：同族产物 `h1`/`h60`=10 键而 `h5`/`h10`/`h20`=4 键（结构不一致），
且 `HANDOVER.md` 仍按旧名一并登记 → **登记与产物不符**。
