### 1. 虚警：一度误判「回填再次挂起」，实为监控口径错误

| 项 | 误判依据 | 纠正 |
|---|---|---|
| 日志无新行 | `meta/l3_backfill_2026-10-13.log` 停在重启横幅 | **Python stdout 走管道是块缓冲**，print 不落盘；"login success!" 是 baostock C 层 fd 直写才可见 → 日志不能当进度信号 |
| 101 秒 0 字节增长 | `stat` 采样窗口内无写入 | flush 节奏是**每 100 只一次**（≈460 KB×100），间隔本就 ~6 min；单次采样 101s 覆盖不到属正常 |
| CPU 40s 增量 0s | 判定「完全阻塞」 | 网络等待态本就 ~0 CPU；健康采集期同样如此 |

**根因（我方的错）**：字节/行比率算错（用了 4.83，实际 **207.7 B/行**）。导致把 "+253k 行" 误读成"+114 只"，进而推导出根本不存在的"停滞"。

### 3. d228865 机制有效性验证（决定性实验）

- 工具：`py-spy dump --pid`（pip install py-spy-0.4.2）定位栈；探针脚本独立进程验证。
- 探针结论（系统 Python 3.13.15）：`setdefaulttimeout(120)` + `bs.login()` 后
  **`default_socket.gettimeout() == 120.0`**，登录 1.3s 成功 → baostock 0.9.3 为纯 Python 包、
  走 stdlib socket，**超时机制对其有效**。
- 挂起最坏耗时重算：单次尝试 ≈ query recv 120s + 退避 + relogin 时 logout 在同一死 socket
  上再等 120s ≈ **~4 min/次 × 3 次 ≈ 12.5 min/只** → 超时后跳过（WARN），不会无限卡死。
  副作用：logout 提前返回不关 socket，每次挂起泄漏 ≤3 个僵连（规模可接受，记录在案）。
- py-spy 栈同时证实：真实抓取栈为 `send_msg → __query_history_k_data_plus_page →
  query_history_k_data_plus → _query → _query_with_retry → _fetch_one_l3 → _fetch_l3`。

### 4. 探针自身 bug（已删 scratch 脚本，教训留档）

`while rs.next(): n += 1` 未调 `rs.get_row_data()` → `cur_row_num` 永不前进 →
`next()` 恒 True → 死循环（线程 active+gil 可观测）。**baostock ResultData 必须
`next()` 与 `get_row_data()` 成对使用**；本项目 `_fetch_one_l3` 的用法是正确的。

### 5. 修正后的监控口径（后续按此执行）

- 单位基准：**207.7 B/行 · 460 KB/只**；
- 停滞告警阈值：**>15 min 无字节增长**才按挂起预案处理（正常 flush 间隔 ~6 min）。
