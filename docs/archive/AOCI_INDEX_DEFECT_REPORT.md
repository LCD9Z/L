# AOCI 索引缺陷报告（目录段被截断，指向另一个仓库）

> **发现时间**：2026-10-11
> **发现场景**：执行 AOCI Fresh Bootstrap 第一批 30 条 Entry 创作之后
> **严重性**：**高（静默失效类）** —— 工具自检报「全部检查通过」
> **当前处置**：**已停止继续创作**（剩余 ~490 条目标绝大多数是嵌套路径，继续会成倍放大该缺陷）

---

## 一、缺陷现象

`aoci.code.txt` 的**目录段头部**（directory section header）对**嵌套路径**发生了截断：
仓库根名 `1.0 - 副本` 被截成 `1.0`（**在第一个空格处截断**）。

### 证据（字节级）

```
$ grep -n "^===" aoci.code.txt
3:===C:/Users/T430/Desktop/1.0 - 副本/===          ← 根目录文件：正确
24:===C:/Users/T430/Desktop/1.0/.github/workflows/===  ← 错：应为 "1.0 - 副本/.github/workflows"
27:===C:/Users/T430/Desktop/1.0/.workbuddy/memory/===  ← 错：应为 "1.0 - 副本/.workbuddy/memory"
```

`od -c` 确认第 24 行字节为 `... D e s k t o p / 1 . 0 / . g i t h u b ...` ——
**没有** ` - ` 与 `副本` 的字节。**不是显示问题，是文件内容问题。**

### ⚠️ 关键：错误段指向的是**另一个真实存在的仓库**

```
$ ls "C:/Users/T430/Desktop/1.0/.github/workflows/ci.yml"
-rw-r--r-- ... 2902 Sep 13 20:37 C:/Users/T430/Desktop/1.0/.github/workflows/ci.yml
```

`C:\Users\T430\Desktop\1.0` 是本机的**兄弟仓库**（`BRANCH_MERGE_REPORT.md` 记录的
另一条演进线）。所以这不是「指向不存在的路径」这种会自然暴露的错误 ——
**它会静默解析到另一个仓库的真实文件上。**

---

## 二、影响面

AOCI 官方 README 明写：**「目录段和 basename 共同解析出 Code 对象身份」**
（`atomic.go[CG9L]` 在 `===.../internal/fs/===` 段内 → `code:internal/fs/atomic.go`）。

因此对**读者侧（模型/人）**：

| 影响 | 说明 |
|------|------|
| **对象身份解析错误** | 按段头解析出的绝对路径指向兄弟仓库，而非本仓库 |
| **跨仓库误读** | 因目标文件真实存在，读者不会察觉错误 |
| **影响面 = 全部嵌套路径对象** | 本仓 522 个受管对象中，**绝大多数**位于 `scripts/`、`pit/`、`risk/`、`factors/`、`tests/`、`reports/`、`docs/` 等子目录 |

### 但有一层是**正确的**

`.aoci/baseline.json` 与机器绑定使用的是**仓库相对路径**，实测正确：

```
$ python -c "...json.load('.aoci/baseline.json')..."
  含 Desktop/1.0/ : 0
  含 Desktop/1.0 - 副本/ : 0
  含 .github/workflows/ci.yml : 1
```

→ **机器身份层（baseline / 绑定 / CAS）未受影响；坏的只是 `aoci.code.txt` 渲染出的段头。**

## 三、为什么是「静默失效」

```
$ aoci doctor --repo "C:/Users/T430/Desktop/1.0 - 副本"
[✓] 仓库根定位: C:\Users\T430\Desktop\1.0 - 副本
[✓] 索引解析: 2 区段 / 30 条目 / 0 解析警告
...
诊断完成: 全部检查通过。
```

**工具自检报「0 解析警告、全部检查通过」** ——
即 AOCI 校验了「段头格式合法」，但**未校验「段头与仓库根是否一致」**。
这与本项目反复出现的缺陷同类：**不报错的失效**。

## 四、已执行与未执行的动作（如实记录）

| 动作 | 状态 |
|------|:---:|
| `aoci scope acknowledge --reviewed-by host_model`（解除 7 项 observe 复核阻塞） | ✅ 已完成 |
| `aoci_maintain` 领取第一批 30 个候选 | ✅ 已完成 |
| 第一批 30 条 Entry 创作并 `aoci_update_entry` 提交 | ✅ **applied 30/30**（先被 `entry_field_budget_exceeded` 拒一次，压缩 2 处 S 后通过） |
| **继续领取第 2..N 批** | ❌ **主动停止** —— 理由见下 |
| 回滚这 30 条 | ❌ 未做（身份层正确，且回滚会丢掉真实产出） |

**为什么停止**：剩余 ~490 个目标里绝大多数是**嵌套路径**，继续创作会：
① 把错误段头扩散到全部条目；② 每批都需重读源码 + 创作语义，成本高；
③ 修工具后需要**重新渲染全部段头**，届时已创作条目越多、返工面越大。
**先修工具，再继续，是成本最低的顺序。**

## 五、根因推断（未能确证，如实标注）

**已确证**：截断点在**第一个空格**（`1.0 - 副本` → `1.0`）；
根目录文件的段头**正确**，只有嵌套路径的段头错误。

**未能确证**：具体代码位置。可排除的：

| 排除项 | 依据 |
|------|------|
| `.aoci/config.json` 存了截断的根 | ❌ 配置中**无** root 字段（运行时发现） |
| 全局仓库注册表 | ❌ `~/.aoci`、`%LOCALAPPDATA%\aoci`、`%APPDATA%\aoci` 均不存在 |
| 我的 `path` 参数写错 | ❌ 我传的是仓库相对路径（`.github/workflows/ci.yml`），符合 Schema 定义 |
| MCP receipt 里的根被截断 | ❌ `runtime_repository_root` = `c:\Users\T430\Desktop\1.0 - 副本`（正确） |
| 行尾/编码问题 | ❌ 三个文件均 LF |

**推断**：嵌套路径的段头由「根路径 + 相对目录」拼接时，**在含空格的根路径上发生截断**；
根目录文件的段头走另一条代码路径（直接用根的原始字符串），故未受影响。

**这是推断，不是结论。** 需 AOCI 作者或源码复核。

## 六、可行的处置方向（供决策，均未执行）

| 方案 | 做法 | 代价 | 风险 |
|:--:|------|------|------|
| **A** | **改仓库目录名去掉空格**（如 `1.0-副本`） | 需重建 `.aoci` 绑定（`runtime_repository_root` 已绑定旧路径）；需同步 MCP 配置里的 `--repo` | 会打断既有绑定；且用户可能不希望改名 |
| **B** | **换一个无空格的路径做试点**，验证「空格是否为唯一触发条件」 | 低（可逆） | 只是验证，不解决本仓问题 |
| **C** | **向 AOCI 作者报缺陷**（GitHub Issue） | 低 | 等待期无法继续创作 |
| **D** | **暂停 AOCI 索引建设**，保留已创作的 30 条 | 低 | 认知层不完整 |
| **E** | 手写/脚本修正 `aoci.code.txt` 的段头 | 低 | **会破坏 AOCI 的 CAS/校验**（正式索引由机器管线写），**不建议** |

**我的建议：B → C 并行。** 先做 B（低成本确证根因），同时向作者报缺陷；
在缺陷确认与修复前**不继续批量创作**。方案 A 需你确认是否接受改名。
